> 来源文件：`ui/`（main_window.py + components/ 共 ~70KB）+ `features/contacts_import/ui/`（7 个文件 ~62KB）
> 目标结构：`frontend/`（Wails v3 默认 vanilla 模板，原生 HTML/CSS/JS，不引前端框架）
> 工作量评级：⭐⭐⭐⭐ —— 全项目唯一"重写"模块，其余都是直译

---

## 1. 为什么 UI 是重写不是直译

PyQt 的控件模型（QWidget/QTableView/QDialog）与 Web 的 DOM 模型完全不同，没有"逐行对照"可言。策略：**按界面功能拆页，逐页重写，UX 对齐（文案/布局/交互顺序）**，视觉可小幅优化。

## 3. 前后端通信模型（Wails 命令）

Python 版是"panel 直接调 processor + UI 直接调 panel"；Go 版是**前端调 Wails 命令**：

```go
// internal/app/handlers.go —— 每个命令一个方法，等价 panel.py 的流程编排函数
type App struct{ /* 依赖注入：excel.Reader, template.Store, settings, license.State */ }

// Bind 注册给前端的命令：
//   ImportListSheets(path) -> []SheetSummary
//   ImportReadSheet(path, sheet, opts) -> excel.SheetData
//   Preview(request) -> core.PreviewData        // 调用 internal/core 纯函数
//   Export(request) -> error                    // 调 internal/excel Writer
//   TemplateList/Get/Save/Delete
//   SettingsGet/SettingsUpdate
//   LicenseActivate(key)/LicenseStatus()/LicenseDeactivate()
//   UpdateCheck()/UpdateDownload()/UpdateApply()
```

**调用规范**：
- 命令参数/返回值全部是 struct/JSON 可序列化类型（Wails 自动处理）
- **命令层是唯一允许捕获并翻译错误的地方**：`errors.Is(err, core.ErrDataProcess)` → 返回 `{code: "DATA_PROCESS_ERROR", message: "..."}`，前端统一弹 toast
- 耗时命令（读取大文件/导出/更新下载）必须返回进度：Wails v3 用 `app.Events.Emit("export-progress", ...)` 事件推送，前端监听
- 长耗时命令前端禁用按钮 + 显示进度，防重复提交

## 4. 页面重写要点（按优先级）

### 4.1 导入向导（核心流程，最先做）

状态机（沿用 Python 版流程）：`选择文件 → 选择 Sheet → 字段映射 → 预览校验 → 导出`。每步一个视图，用简单的 `showStep(i)` 函数切换，不引路由库。

### 4.2 字段映射表（交互最重）

- Python 版 `mapping_table.py` 有自动匹配（调 template matcher）+ 手动下拉
- 前端：表格 + 每行 `<select>`，自动匹配结果预填；**匹配算法在 Go 侧跑**（`internal/template`），前端只展示
- 对齐点：自动匹配的"命中/未命中"视觉区分要与 Python 版一致

### 4.3 预览表

- 10 万行数据不要全量渲染 DOM：**只渲染前 200 行 + 行数统计**，加"加载更多"或简单虚拟滚动（`content-visibility` 或分页渲染）
- 异常提示区（`detect_truncated_numbers` 的提示文本）原样展示

### 4.4 设置页

6 个 tab 直译（导入/导出/日志/更新/关于/内置），表单保存调 `SettingsUpdate` 命令，读 `SettingsGet`。

## 5. 关键实现决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 前端框架 | **原生 JS + Vite**（Wails vanilla 模板） | 页面量小（~10 个视图），无状态管理需求；框架 = 多余依赖 |
| CSS | 手写 + CSS variables | 主题切换用变量，不引 Tailwind |
| 大表格 | 分页渲染（200 行/页） | 避免 10 万 DOM 节点卡死 WebView |
| 文件对话框 | Wails `OpenFileDialog`（原生） | 与 QFileDialog 体验一致 |
| 进度 | Wails Events 推送 | 导入/导出/更新的实时进度 |
| i18n | `i18n.js` 键值映射（中文） | 一次到位，将来加英文只加映射 |
| 组件 | 函数组件 + 模板字符串 | 无构建期框架，`innerHTML` 受控使用（数据用 `textContent` 防注入） |

**安全注意**：Excel 单元格内容可能含 `<script>`，渲染进 DOM 一律 `textContent`/`escapeHtml`，禁止 `innerHTML` 直接拼用户数据（xlsx 注入攻击是真实威胁，WPS 用户常打开不可信表格）。

## 6. 迁移步骤（L5）

1. **UI 盘点**：产 `ui-inventory.md`（§2 输出物），逐条过 Python 版确认交互
2. **骨架**：`wails init` 模板改造为左侧导航 + 页面容器
3. **核心流程**：导入向导（选文件→Sheet→映射→预览→导出）端到端跑通——这是 MVP 红线
4. **外围页面**：模板管理 → 设置 → 更新 → 关于
5. **UX 打磨**：toast、状态栏、空态、加载态、错误提示对齐 Python 版
6. **手工验收**：对照 `ui-inventory.md` 逐条打勾

## 8. 注意事项

1. **不要引前端框架**：一旦引入 React/Vue，依赖树和构建复杂度翻倍；本应用页面量小，原生 JS 完全够（`ponytail:` 注释标注：若未来页面超 30 个或需要复杂状态管理，再评估引入）
2. **XSS 防护**：所有用户数据（Excel 单元格/文件名/模板内容）渲染必须转义
3. **WebView 差异**：macOS WKWebView vs Windows WebView2 渲染差异（滚动条/字体）——用 CSS reset + 通用属性，不用 `-webkit-` 私有前缀
4. **中文输入法**：WebView 下输入框 IME 一般正常，但 macOS 下个别版本有光标 bug——若遇到，用 `compositionstart/end` 事件规避（已知问题，提前知道）
5. **dev 模式**：`wails dev` 前端热更新，CSS/JS 改动秒刷；Go 改动需重启后端——开发节奏与 Python 版完全不同，团队要适应
